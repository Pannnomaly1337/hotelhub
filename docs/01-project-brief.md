# Project Brief

## Section 1: Project Overview

### 1.1 Project Name:

    HotelHub

### 1.2 One-line Description:

    ระบบ PMS สำหรับจัดการโรงแรมบริหารเองขนาดเล็กถึงขนาดกลาง พร้อมระบบแดชบอร์ดที่อัพเดตแบบเรียลไทม์ พร้อมป้องกันการเกิด Over booking และข้อผิดพลาดทางธุรกิจพร้อมการทำ Dynamic pricing เพื่อเพิ่มรายได้

### 1.3 Elevator Pitch:

จากการสำรวจพบว่าโรงแรมขนาดเล็กไปจนถึงขนาดกลางที่เจ้าของเป็นคนบริหารเองในประเทศไทยยังมีระบบการบริหารจัดการภายในโรงแรมที่ยังคงมีช่องโหว่อยู่ เช่น

- การอัพเดตสถานะของสิ่งต่างๆ ภายในโรงแรม เช่น สถานะห้องพัก ประวัติการจองห้องพักและงานของแม่บ้าน เหล่านี้ยังคงใช้รูปแบบกระดาษหรือโทรศัพท์เพื่อดำเนินการอยู่

ช่องโหว่นี้อันตรายสำหรับธุรกิจ เช่น ทำให้เกิดการจองห้องพักซ้ำกันหรือเกิดการเสียโอกาสในการบริการลูกค้าเพราะ Work load ของพนักงานในบางตำแหน่งที่มีมากเกินไป

ซึ่ง HotelHub ออกแบบมาเพื่อปิดช่องโหว่นี้ด้วย

- แดชบอร์ดแสดงการจัดการภายในโรงแรมที่อัตเดตสถานะแบบ**เรียลไทม์**
- ระบบ**ป้องกันการเกิดข้อผิดพลาดทางธุรกิจ**อย่างครบถ้วน
- โอกาสในการทำกำไรที่มากขึ้นจากการทำ **Dynamic pricing**

เหมาะสำหรับโรงแรมขนาดเล็กไปจนถึงขนาดกลางที่ต้องการเปลี่ยนมาใช้ระบบ PMS ในการจัดการแบบครบวงจรในราคาที่ถูกลงและยังสามารถรองรับการบริการที่มีขนาดใหญ่ขึ้นในอนาคตได้อีกด้วย

## Section 2: Problem Statement

### 2.1 ปัญหาที่ HotelHub แก้:

- P0: การเกิดปัญหา Over booking จากการนำเข้าข้อมูลจากหลายที่ เช่น
    - จากการจองออนไลน์ผ่านเว็บไซต์ของโรงแรม
    - จากการโทรศัพท์เพื่อจองห้องพัก
    - จากการ Walk-in
    
    นั่นอาจจะทำให้ห้องพักที่ลูกค้าต้องการสามารถถูกจองซ้อนกันได้ จนนำไปสู่การยกเลิกการจองและต้องคืนเงินให้ลูกค้า ทำให้โรงแรมสูญเสียรายได้และได้รับรีวิวที่ไม่ดีอีกด้วย
- P1: งาน (Task) ที่ตำแหน่งแม่บ้านจะต้องทำล้นมือในแต่ละวันและขาดการจัดสรรแบ่งงานอย่างมีประสิทธิภาพ ทำให้ไม่สามารถสรุปได้ว่าในแต่ละวันจะต้องทำงานอะไรบ้าง ทำให้ในบางครั้งเกิดการตกหล่นของสิ่งที่จะต้องทำและถ้าหากเป็นสิ่งสำคัญ เช่น ความต้องการ (Request) บางอย่างของลูกค้าก็อาจจะนำไปสู่การรีวิวที่ไม่ดีได้
- P1: จะต้องมีการวิทยุหรือสอบถามกันโดยตรงตลอดเวลาระหว่างตำแหน่งพนักงานหน้าเคาท์เตอร์ (Frontdesk) และแม่บ้านว่า สถานะห้องพักของลูกค้าที่กำลังจะทำการเช็คอินเรียบร้อยแล้วหรือยัง ทำให้เกิดความล่าช้าในการทำงานและอาจทำให้เสียโอกาสในการบริการที่ราบรื่น
- P0: พนักงานตำแหน่ง Frontdesk ทำงานอย่างหนักเพราะจะต้องตรวจสอบการจองห้องพัก (booking) ของลูกค้าและจะต้องกดเปลี่ยนสถานะของห้องพักห้องนั้นๆ ด้วย ซึ่ง 1 คนที่จะต้องทำหลายอย่างพร้อมกันในเวลาเดียวกันอาจจะนำไปสู่การทำงานที่ผิดพลาดได้
- P1: ไม่กล้าซื้อระบบ PMS ที่มีขายในตลาดเพราะความกลัวว่าจะมีราคาและค่าดูแลที่สูงมากเกินไป
- P2: ในช่วงเทศกาลที่จะมีลูกค้าหลั่งไหลเข้ามามากมาย ส่งผลให้เกิดโหลดของการทำงานที่มากขึ้น ทำให้พลาดโอกาสในการทำกำไร

### 2.2 ทำไมปัญหาเหล่านี้สำคัญ:

ในปี 2026 (จากข้อมูลล่าสุด) ประเทศไทยมี**โรงแรมที่มีการบริหารจัดการด้วยตัวเองที่กิน Market share ประมาณ 57.65% นั่นคือมากกว่าครึ่งหนึ่งของตลาด ซึ่งเป็นโรงแรมขนาดเล็กถึงขนาดกลางถึงประมาณ 47.58% และยังไม่มีการใช้งานระบบ PMS กันเยอะ (แหล่งที่มี: Mordor Intelligence, 2026)** ทำให้ปัญหาเรื่องการบริหารจัดการงานเกิดขึ้นได้ตลอดเวลา เช่น
- เกิดการจองห้องพักซ้ำ (Over booking)
- การตกหล่น Request สำคัญของลูกค้า
- ปัญหาการสื่อสาร
- การจัดการกับ Task ที่จะต้องทำภายในโรงแรม
- Workload ที่มากเกินไปของพนักงานตำแหน่ง Frontdesk

ซึ่งปัญหาเหล่านี้อาจนำไปสู่การรีวิวในแง่ลบให้กับโรงแรมได้ เช่น การถูกรีวิวเพียง 1 - 2 ดาวเพราะได้รับการบริการที่ไม่น่าพึงพอใจ ส่งผลให้ลูกค้าท่านอื่นที่เข้ามาดูรีวิวคะแนนโรงแรมของเราแล้วอาจจะไม่ต้องการเข้าพัก ทำให้เสียโอกาสในการสร้างรายได้ทางธุรกิจและถ้าเป็นช่วงเทศกาล ผลเสียเหล่านี้อาจจะทำให้โรงแรมถูกลดความสามารถในการแข่งขันออกไป

## Section 3: Target Users

### 3.1 Primary User (User หลักของระบบ)

- คุณ A พนักงานเคาท์เตอร์ (Frontdesk)

- อายุ 27 ปี มีประสบการณ์ในการใช้งานคอมพิวเตอร์ในระดับกลางและเคยใช้งานระบบ PMS จากตำแหน่งงานที่เคยทำก่อนหน้านี้และเคยใช้ Cloundbeds มาก่อน

- การทำงานหลัก: รับการจองห้องพักของลูกค้าจากทั้งทางโทรศัพท์และการ Walk-in ประมาณ 10 - 20 คนต่อวันและหากเป็นช่วงเทศกาลจำนวนลูกค้าอาจจะสูงสุดถึง 30 - 40 คนต่อวันและจะต้องเช็คสถานะความพร้อมของห้องพักก่อนที่จะรับเช็คอินหรือเช็คเอาท์ทุกครั้ง รวมไปถึงการทำชำระเงินพร้อมทั้งดู Request ต่างๆ จากลูกค้าที่มาเข้าพักด้วย ซึ่งขั้นตอนเหล่านี้จะต้องทำให้เสร็จไม่เกิน 5 นาทีต่อลูกค้า 1 ชุด เพื่อไม่ให้คิวรอนานเกินไป

- Pain point: ในแต่ละวันจะต้องเปิดข้อมูลการจองห้องพักผ่านโปรแกรม Microsoft Excel เพื่อดูว่าในวันที่เท่าไรบ้างจะมีลูกค้าเข้ามาเช็คอินและเช็คเอาท์ มีลูกค้ากี่ท่านที่เข้ามาพักพร้อมตรวจสอบ Request พิเศษจากลูกค้าแต่ละท่าน พร้อมทั้งโทรหาพนักงานในตำแหน่งแม่บ้านเพื่อสอบถามว่าสถานะห้องพักที่ลูกค้าต้องการพร้อมที่จะเข้าพักแล้วหรือยัง ซึ่งในวันปกติก็ค่อนข้างที่จะต้องทำงานหลายอย่างอยู่แล้ว ถ้าเป็นช่วงเทศกาลก็จะมีทั้งลูกค้าที่ทั้งโทรศัพท์และ Walk-in เข้ามาจองห้องพักเยอะมาก ทำให้เกิดปัญหา Workload ของการทำงานที่มากขึ้นและอาจเกิดความผิดพลาดในการจัดการดูแลลูกค้า ส่งผลให้ลูกค้าต้องรอนานเนื่องจากจะต้องเช็คข้อมูลต่างๆ จากหลายโปรแกรม เช่น
    - โปรแกรม Microsoft Excel
    - สมุดจดบันทึก

    ซึ่งในบางครั้งก็ให้ข้อมูลที่ไม่ตรงกันอีกด้วย

- ต้องการ**ระบบหรือโปรแกรมบางอย่างที่สามารถเรียกดูข้อมูลสถานะความพร้อมของห้องพักทั้งโรงแรมในหน้าจอเดียวแบบเรียลไทม์** เพื่อที่จะได้ลดการสื่อสารที่ไม่จำเป็นออกไปและยังสามารถประหยัดเวลาและสามารถทำการรับเช็คอินและเช็คเอาท์ให้ลูกค้าได้เร็วมากขึ้น แม่นยำมากขึ้นและลดโอกาสที่จะเกิดข้อผิดพลาด

### 3.2 Secondary Users:

- **Guest**: User เข้าเว็บไซต์มาเพื่อดูสิ่งที่ตนต้องการ เช่น
    - ดูหน้าตาและราคาของห้องพัก
    - ประวัติของโรงแรม
    - รีวิวของโรงแรม
    - ทำเลที่ตั้งของโรงแรม
    - และอื่นๆ ที่เกี่ยวข้อง

    แต่จะยังไม่สามารถทำการจองห้องพักหรือเขียนรีวิวได้ จะต้องทำการ Register และ Login เพื่อเข้าสู่ระบบมาก่อน

- **Customer**: User ที่ทำการ Login เพื่อเข้าใช้งานระบบของโรงแรม เช่น การจองห้องพัก (Booking room) แบบออนไลน์และทำการชำระเงิน (เพื่อที่ในวันเข้าพักก็สามารถยื่นเอกสารการยืนยันตัวตนก็สามารถเข้าพักได้) พร้อมทั้งสามารถเขียนรีวิวให้กับโรงแรมได้และสามารถยกเลิกห้องพักได้หากไม่ต้องการแล้ว (ตาม Cancellation Policy ของโรงแรม)

- **Housekeeping**: User แม่บ้านที่จะเข้ามาเช็คในระบบโรงแรมในแต่ละวันว่า วันนี้จะต้องทำงาน (Task) ใดที่ห้องพักไหนบ้าง พร้อมการอัพเดตผลการทำงาน (สถานะของห้องพัก) หากทำงานนั้นๆ เสร็จแล้วและหากเกิดปัญหาขึ้นกับห้องพักหรือต้องการ Requirement พิเศษก็สามารถเขียนรายงานเข้าไปในระบบเพื่อจัดการกับ Requirement ได้ เช่น
    - การแจ้งปัญหา
    - แจ้งสิ่งที่ต้องการในการทำงาน


- **Manager**: User ที่สามารถเช็คข้อมูลต่างๆ ภายในโรงแรม เช่น
    - ข้อมูลทางการเงิน
    - สถิติการเข้าพัก
    - อ่านรีวิวจากลูกค้า
    - ดูประวัติการทำงานของเจ้าหน้าที่ (Staff) ในตำแหน่งต่างๆ

    เพื่อที่จะได้จัดทำเป็นรายงานเสนอต่อ User ตำแหน่ง Admin (เจ้าของโรงแรม) พร้อมทั้งสามารถ

    - ตั้ง Dynamic pricing rules ในแต่ละช่วงเวลาได้
    - ออกแบบและจัดการกับ Staff schedule ได้
    - ทำการตัดสินใจที่สำคัญต่างๆ เช่น อนุมัติการคืนเงินลูกค้าและการทำส่วนลดให้ลูกค้า VIP ได้
    - สามารถทำการปิดห้องพักชั่วคราวเพื่อปรับปรุงห้องพัก
    - สามารถเข้าถึงประวัติการทำงานของ Staff ได้ (Audit logs) ยกเว้นตำแหน่งของตัวเอง ซึ่งจะไม่สามารถแก้ไขและลบ Audit logs นี้ได้ จะทำได้แค่เพียงเรียกดูเท่านั้น

- **Admin**: User เจ้าของโรงแรมที่สามารถทำได้ทุกอย่างที่ Manager ทำได้และสามารถ
    - จัดการห้องพัก: เพิ่ม/ลด/แก้ไข ห้องพักทั้งหมดได้
    - สามารถตั้งประเภทและราคาของห้องพักได้
    - สามารถจัดการกับตำแหน่ง Manager ได้ เช่น จ้าง/ไล่/ดูประวัติการทำงาน (Audit logs) ได้
    - เข้าถึงประวัติการทำงานของ Staff ได้ทุกตำแหน่งแต่จะไม่สามารถแก้ไขและลบ Audit logs นี้ได้ จะทำได้แค่เพียงเรียกดูเท่านั้น

## Section 4: Core Features (MVP)

### F1: Authentication & Authorization (RBAC)

- **Who**: Customer, Frontdesk, Housekeeping, Manager และ Admin

- **What**:
    - User สามารถสมัครสมาชิก (Register) เพื่อทำการลงทะเบียนเป็นสมาชิกกับระบบเพื่อเข้าใช้งานได้
    - User มี Role เป็นของตนเองสำหรับการเข้าถึงข้อมูลและ Features ต่างๆ ได้

- **Why MVP**: ในการที่จะสามารถเข้าถึงแต่ละ Features จะต้องมีการสมัครสมาชิกเพื่อเป็นการยืนยันตัวตนและมีระบบ RBAC เพื่อใช้ในการแยกแต่ละ Role เพื่อสิทธิ์ในการเข้าถึง Features ต่างๆ ที่แตกต่างกัน

- **Out of MVP**: ไม่มี

- **Dependencies**: ไม่มี เพราะเป็น Feature แรกที่จะต้องมีการพัฒนาเกิดขึ้น

### F2: Room Catalog & Search

- **Who**: Guest, Customer และ Frontdesk

- **What**:
    - User สามารถดูรายละเอียดต่างๆ ของห้องพักที่ต้องการได้
    - User สามารถใช้การค้นหาโดยการกรอง (Filter search) หรือสามารถกรอกชื่อห้องพักที่ต้องการได้
    - เป็นขั้นตอนที่จะนำไปสู่การทำ Booking ในลำดับถัดไป

- **Why MVP**: เป็น Core feature ของโรงแรมเพื่อให้ User สามารถค้นหาห้องพักที่ตนเองต้องการได้

- **Out of MVP**: ไม่มี

- **Dependencies**: ไม่มี

### F3: Online Booking (Customer flow)

- **Who**: Customer

- **What**:
    - User สามารถเลือกห้องพักที่ตนเองต้องการพร้อมทั้งสามารถกรอกข้อมูลที่จำเป็นต้องใช้และกดจองห้องพักได้
    - เป็นขั้นตอนที่จะไปเรียกการทำงานของ feature Email notifications เพื่อให้ User ได้รับการแจ้งเตือนทาง Email ว่าได้ทำการจองห้องพักเรียบร้อยแล้ว (Triggerd event)

## Section 5: Killer Features (Differentiators)

### Killer 1: Real-time Operations Dashboard

- **Problem it solves**:

    เพื่อ**ลดการสื่อสารที่ไม่จำเป็นในการทำงานออกไปบางส่วน** เช่น การโทรศัพท์หรือวิทยุหากันเพื่อยืนยันหรือสอบถามข้อมูลสถานะของห้องพักว่าเรียบร้อยดีแล้วหรือยังและ**ลดการสื่อสารที่อาจจะทำให้เกิดข้อผิดพลาด**ได้ เช่น
    - สื่อสารกันผิดภาษา
    - สื่อสารกันอย่างไม่ชัดเจน
    
    ก่อนที่จะมีการส่งงาน ซึ่งการมาถึงของเรียลไทม์ Dashboard เพียงแค่มองก็จะทำให้สามารถเข้าใจการทำงานได้เองโดยอัตโนมัติ

- **How it works**:

    ใช้ **WebSocket** ในการอัพเดตสถานะ หากพนักงานตำแหน่งแม่บ้านกดอัพเดตสถานะของห้องพัก ฝั่ง Backend จะสั่งการอัพเดตไปที่ฐานข้อมูล (Database) และเกิดเป็น Event ผ่าน WebSocket แล้วหาก Client ไหนที่ทำการสมัครรับ (Subscribe) เอาไว้ ก็จะได้รับการเกิดขึ้นเองของ Event นั้นทันทีโดยที่ไม่ต้องกด Refresh ซึ่ง UI ก็จะ**มีการอัพเดตโดยอัตโนมัติ**ด้วยเช่นเดียวกัน

- **Technical challenges**:

    - การจัดการกับการเชื่อมต่อ (Connection management) เช่น
        - จะออกแบบการเชื่อมต่ออย่างไรหรือจะต้องมีใครบ้างที่จำเป็นต้องทำการ Subscribe เอาไว้อยู่ตลอดเวลา
        - เมื่อคำนวณกับค่าใช้จ่ายกับค่า Resource ต่างๆ แล้ว มีความคุ้มค่าหรือไม่
        - ถ้าหากต้องการที่จะวางแผนการทำการขยายการเชื่อมต่อ (Scale) จะต้องทำอย่างไร
        - ปัญหาหากหลุดการเชื่อมต่อไปกลางคันจะมีการทำ Reconnection อย่างไร
        - จะเชื่อม (Sync) ข้อมูลเดิมกับข้อมูลใหม่อย่างไร

    - Race condition: หากมีการอัพเดตสถานะพร้อมกัน 2 ที่หรือมากกว่านั้น จะให้การแสดงผลของที่ไหนเป็นฝ่ายชนะ (Optimistic locking จะสามารถแก้ไขปัญหานี้ได้หรือไม่)

### Killer 2: Dynamic Pricing Engine

- **Problem it solves**:

    ใน**ช่วงเวลาที่แตกต่างกัน ที่พักจะกลายเป็นทองคำที่ลูกค้าต้องการ**และถ้าโรงแรมอยู่ในทำเลทองที่สะดวกต่อการเดินทางมาเข้าพักอยู่แล้ว การทำ Dynamic pricing จะเป็นสิ่งที่ดีมากสำหรับธุรกิจของเรา เม็ดกำไรจากการตั้งราคาของห้องพักที่สูงขึ้นในแต่ละช่วงเวลาและราคาที่ต่ำลงบ้างเสมือนการลดราคา จะมีผลดึงดูดความสนใจจากลูกค้าให้มีมากขึ้น

- **How it works**:

    ราคาของห้องพักจะเปลี่ยนแปลงไปในแต่ละช่วงเวลา เช่น
    - Occupancy rate: เมื่อห้องว่างเหลือน้อยจะทำให้ราคาห้องพักปรับตัวเพิ่มสูงขึ้น
    - Day of week: ช่วงสุดสัปดาห์ราคาห้องพักจะสูงกว่าช่วงต้นสัปดาห์
    - Booking lead time: จองห้องพักวันนี้แล้วหากเข้าพักภายในวันนี้จะได้ราคาพิเศษ
    - Length of stay: อยู่พักยาว (3 วัน/ 7 วัน) จะได้รับส่วนลดห้องพักพิเศษ
    - Season: ราคาห้องพักที่แตกต่างกันในช่วงเวลาเทศกาล (High/Low season)
    - Holiday/Event: ช่วงวันหยุดหรือกิจกรรม (Event) ต่างๆ เช่น งานวิ่งมาราธอน, งานคอนเสริตและงานประเพณีเป็นต้น

    นั่นทำให้สามารถสร้างกำไรจากราคาห้องพักธรรมดาได้เพิ่มมากขึ้นกว่าช่วงเวลาปกติที่จะแค่คงที่อยู่ตลอดเวลา

- **Technical challenges**:

    - Rule engine design: จะออกแบบ Logic ยังไงให้ครอบคลุมกับเงื่อนไขในช่วงราคาห้องพักที่ต้องการและถ้าหากมีกฏราคาอันใหม่มา จะต้องทำอย่างไรให้สามารถใช้งานกฏใหม่นั้นๆ ได้เลยโดยที่ไม่ต้องเขียน Code เพิ่ม
    - Priority of rules: ถ้ามีกฏของราคา 2 อันชนกันและจะต้องมีการใช้งานในวันเดียวกัน กฏไหนจะชนะ
    - การตั้งราคา: ราคาห้องพักจะต้องมีราคาไม่ต่ำกว่าต้นทุนเดิม (ข้อมูลจาก Base cost ที่จะมีอยู่ใน Room type) และราคาห้องพักจะต้องไม่มากไปกว่า X%
    - การเก็บประวัติการตั้งราคาแบบ Dynamic: ให้เก็บราคาตอนที่ลูกค้ากดจองห้องพัก (จะไม่เก็บราคาห้องพักปัจจุบัน) และการเก็บข้อมูลจะเก็บลงใน Database ใดและจะมีการออกแบบอย่างไรเพราะข้อมูลจะมีเยอะมาก
    - ตอนที่ลูกค้ากำลังจะกดชำระเงิน ราคาห้องพัก ณ ตอนนั้นจะต้องถูก Freeze เอาไว้ทันทีที่ลูกค้ากดยืนยัน (เสมือนการแลกเงินตราต่างประเทศ เพื่อป้องกันลูกค้าเห็นราคาผิดหากดึง Pricing rule ใหม่ตลอดเวลา) จะต้องมีการออกแบบอย่างไร

### Killer 3: Audit log & Activity Timeline

- **Problem it solves**:

    เพื่อเรียกดูประวัติการทำงานของพนักงาน (Staff) แต่ละคนว่า ใคร ทำอะไร ที่ไหนและเวลาใด เพื่อนำมาประเมินความขยันในการทำงานหรือคำนวณความเสียหายหากเกิดขึ้นจริงหรือประวัติการทำงานของ Staff บางคนที่ถูกลูกค้า Complain มา ซึ่ง Feature นี้จะเสมือนว่าเป็น Log ว่าเกิดอะไรขึ้นบ้างในการทำงานของ Staff แต่ละคน

- **How it works**:

    จะทำการเก็บข้อมูล Log ที่เกี่ยวกับ:
    - user_id
    - action
    - entity
    - before
    - after
    - timestamp
    - ip_address

    นี่จะเป็น Log พื้นฐานที่ครบถ้วนว่าใคร ทำอะไร ที่ไหนและเวลาใด โดยจะเก็บ Log เหล่านี้ไว้ในตาราง audit_logs ใน Database เดียวกัน เพราะง่ายและสามารถ JOIN กับตาราง user และ entity อื่นๆ ได้ (แต่นั่นจะทำให้ Database ของเราโตเร็วและอาจมีค่าใช้จ่าย (Cost) ตามมาเร็วและมากกว่าเดิม) และการเก็บ Log จะเก็บนานตาม Retension policy ของประเทศไทย

- **Technical challenges**

    การออกแบบความเชื่อมโยงถึงกันในแต่ละหน้า ที่จะต้องมีการออกแบบให้ดีกว่า Log ใดควรที่จะเก็บและไม่จำเป็นที่จะต้องเก็บก็ได้ เพื่อที่จะไม่ให้เป็นการจัดเก็บข้อมูลมากเกินความจำเป็น ซึ่งก็จะมีเรื่องของค่าใช้จ่าย Database เข้ามาเกี่ยวข้องด้วย

    - Performance impact: จะมีผลกระทบมากขึ้นด้วยเพราะว่า Database จะต้องมีโหลด (Load) เพิ่มอีกเท่าตัว
    - จะทำการ Enforce log เหล่านี้อย่างไรให้ไม่มีใครสามารถแก้ไขข้อมูลใดๆ ได้ (แม้แต่ Admin) นั่นคือสามารถดูได้แค่อย่างเดียวเฉพาะผู้ที่มีสิทธิ์ถึงเท่านั้น
    - Async & sync logging: จะเลือกวิธีใดในการเก็บข้อมูล (ในแง่ของความเร็วและความถูกต้องครบถ้วนของข้อมูล)
    - Filtering & search: แน่นอนว่าข้อมูลจะต้องสามารถค้นหาได้อย่างรวดเร็วเพราะ Log ที่มีจะเยอะมากและจะมีการจัดการกับ Index หรือแนวทางอย่างไรให้สามารถทำ Query ข้อมูลได้อย่างรวดเร็ว

## Section 6: Tech Stack + Justification

### Frontend Framework:

- NextJS: เป็น Modern framework ที่อำนวยความสะดวกในสิ่งต่างๆ เช่น
    - การขึ้นโปรเจคใหม่
    - การ Setup library
    - การทำ Routing
    - Render on server
    - SEO

    เหมาะกับเว็บโรงแรมที่มีการแสดงผลของรูปภาพเยอะ

- TypeScript: ทุก Logic จะต้องมีการทำ Validation ชนิดของข้อมูล การเลือกใช้ TypeScript จะเป็นการจัดการในด้านนี้ เนื่องจากการใช้เพียง JavaScript อาจจะทำให้เกิด Type mismatch ที่อาจจะนำไปสู่การเกิดบัค (Bug) ที่ส่งผลต่อ Business ในระดับ Production ได้

- TailwindCSS: เป็นมาตราฐานการตกแต่งของเว็บไซต์สมัยใหม่ซึ่งเขียนได้ง่ายกว่า เร็วกว่า CSS แบบ Traditional

- Shadcn/UI: มี Library ของ NextJS ที่รองรับในการใช้งานอยู่แล้ว สามารถนำ Code ของส่วนประกอบ (Component) ต่างๆ ที่ต้องการมาใช้งานได้เลยแถมยังสามารถทำงานร่วมกันกับ TailwindCSS ได้อีกด้วย

- Zod: เป็น Schema validation library นั่นคือทุกการกรอกฟอร์ม (Form) จาก User หรือการทำ API request ต่างๆ จะต้องผ่านการทำ validation ก่อนเกิดการยืนยัน (Submit) โดย Zod และยังสามารถใช้ TypeScript types กับ Runtime validation มา Sync ต่อกันได้

- React Hook Form: ใช้ในการจัดการกับ Form state ต่างๆ เพื่อให้ React มีการ Re - render ที่น้อยลงและเป็นการประหยัด Resource ด้วย ซึ่งสามารถใช้งานร่วมกับ Zod ได้

- TanStack Query (React Query): ใช้ในการจัดการกับ Server state (ข้อมูลที่มาจากการเรียกใช้ API ที่มีการคืนค่า (Return)) พร้อมทั้งการจัดการกับการทำ Caching, Refetching และ Optimistic update ได้อีกด้วย ซึ่งจะมาใช้แทน useEffect และการ Fetch ข้อมูล

### Backend Framework:

NestJs + TypeScript: เพื่อจัดการกับความถูกต้องของชนิดของข้อมูลโดย TypeScript และ NestJs ยังเป็น Framework ที่เหมาะกับการทำโปรเจคใหญ่ เพราะ

- Modular architecture: มีการแบ่ง Code ออกเป็น Module ต่างๆ เช่น UserModule และ RoomModule เป็นต้น
- Decorators: Syntax ที่ใช้มีความ Clean มาก ทำให้สามารถอ่าน Code แล้วทำความเข้าใจและดูแลรักษาได้ง่าย
- มี Built - in เช่น Validation ของ Class - validator และ WebSocket ในการทำ Killer feature #1
- Maintenence: เนื่องจากโปรเจคนี้ใหญ่ มีหลาย Module และมี Structure ที่ชัดเจนและซับซ้อน ทำให้ NestJs มีความเหมาะสมมากในการใช้งานในระยะยาว

### Database

PostgreSQL: เพราะระบบการจัดการโรงแรมในแต่ละข้อมูลของแต่ละฝ่ายจะมีการเชื่อมต่อถึงกันอย่างชัดเจน เช่น จาก Customer ไปหา Booking ไปหา Payment หรือจาก Task ไปหา Dashboard ไปหา Housekeeping นั่นคือ

- แต่ละข้อมูล/ตารางมีการเชื่อมต่อ มีความสัมพันธ์กันอย่างชัดเจน นั่นทำให้ PostgreSQL (SQL) ทำหน้าที่ได้ดีกว่า Datase แบบ NoSQL
- การทำ ACID Transaction รวมไปถึงคำสั่ง Query ต่างๆ ที่จะต้องเกิดการ JOIN กันของตารางสามารถทำได้ง่ายกว่าด้วย
- มีการจัดการกับการทำ Row - level locking ได้ (เผื่อในกรณีที่เกิดการ Booking พร้อมกันจากหลาย User) ก็จะทำการล็อคการ Booking นั้นๆ ไปเลยแถมเป็นการป้องกันการเกิด Race condition อีกด้วย
- สามารถทำ Full - text search ได้สำหรับการค้นหาห้องพัก

### Object-Relational Mapping (ORM)

PrismaORM: ทุกการทำ Query ที่จะต้องมีการติดต่อกับ Database เราจะไม่ให้ Backend ติดต่อกับ Database โดยตรง แต่จะทำการผ่าน ORM แทน เพื่อให้การติดต่อส่งและดึงข้อมูลเป็นไปตามแบบ Protocol ที่ได้ออกแบบเอาไว้ (Type-safe queries) ซึ่งเป็นการป้องกันไม่ให้เกิด Bug ที่ไม่คาดคิดต่างๆ เกิดขึ้นที่อาจจะส่งผลกระทบในอนาคตและมี Studio UI สำหรับใช้ในการดูและจัดการกับ Database โดยตรง

### Auth Strategy

ใช้ Bcrypt ในการทำ Password hashing เพราะจะไม่มีการเก็บ Original password ของ User เอาไว้ใน Database โดยตรงเพราะเสี่ยงในด้านของความปลอดภัยและนโยบายส่วนตัวหากเกิดการรั่วไหลของข้อมูล นั่นคือจะต้องมีการทำ Password hashing แล้วเก็บลงใน Database แทนและหากมีการ Login จาก User เข้ามาก็จะทำการเปรียบเทียบ (Compare) ระหว่าง Original password ที่ User กรอกเข้ามานำมา Hash แล้วเอาไปเปรียบเทียบกับ Hashed password ที่มีอยู่แล้วใน Database ซึ่งหากตรงกันในลำดับถัดไปจะให้ JWT ทำการออก (Sign) Token เพื่อใช้แทนข้อมูลในการยืนยันตัวตนโดยที่ไม่ต้องไปดึงข้อมูลมาจาก Database ซ้ำๆ เพื่อตรวจสอบว่าเป็น User ใด โดย Token นี้จะออกโดย JWT ที่ใช้ Secret key ซึ่งจะเป็นความลับแล้วนำ Token นี้ไปใช้ในแต่ละ Request ที่ User ร้องขอ (Request) ออกไป เป้นการทำ RBAC เพื่อจำกัดสิทธิ์ในการเข้าถึงข้อมูลและ Feature ต่างๆ ของ User แต่ละคนด้วย

- มีระบบ Access token และ Refresh token:
    - Access token: มีอายุสั้น (ประมาณ 15 นาที) ใช้ส่งไปในทุก Request ซึ่งจะจัดเก็บใน httpOnly cookie หรือจัดเก็บใน Memory ก็ได้
    - Refresh token: มีอายุยาว (เริ่มต้นที่ 7 - 30 วัน) ใช้เพื่อทำการขอ Access token ใหม่ ซึ่งจัดเก็บใน httpOnly cookie เท่านั้นเพื่อความปลอดภัย

- โดยจะมี Flow ของการทำงานดังนี้
    - User ทำการ Login แล้วได้ Access token และ Refresh token
    - ในทุกการทำ Request จาก User จะทำการส่ง Access token แนบไปด้วย
    - หาก Access token หมดอายุ ระบบจะทำการส่ง Refresh token เพื่อขอ Access token อันใหม่
    - และถ้าหาก Refresh token หมดอายุ User จะต้องทำการ Login เข้ามาใหม่อีกครั้ง

- สาเหตุที่จะต้องแยกออกเป็น 2 tokens เพราะว่า
    - หากมีการรั่วไหลของ Access token ตัว Attacker จะมีเวลาเพียง 15 นาที (หรือตามค่าเวลาที่ตั้งไว้) ตามอายุของ Access token ซึ่งความเสี่ยงก็จะขึ้นตามช่วงเวลาที่ระบบตั้งค่าไว้
    - Refresh token ถูกเก็บไว้ที่ httpOn;y cookie เพื่อป้องกันการเกิด XSS จากการทำ JS access

### Real - time:

    - มีการแจ้งเตือนผลเกิดขึ้น

## Section 7: Out of Scope (สิ่งที่จะไม่ทำในตอนนี้)

- Multi-property: ไม่ทำ เพราะอยากจะโฟกัสที่โรงแรมเดียวก่อน เพื่อให้สามารถใช้เวลาและความละเอียดให้ได้มากที่สุด แล้วจากนั้นจะทำการอัพเดตให้สามารถรองรับได้หลาย Property ใน Version ถัดไป

- Mobile native app: ไม่ทำ เพราะจะโฟกัสไปที่ Responsive design web ก่อน ซึ่งสามารถเข้าใช้งานได้ในทุกอุปกรณ์ (รวมถึงใน Mobile แบบ Web browser ด้วย) เพราะอยากจะทำแบบในเว็บเป็นหลักไปก่อนแล้วจะมีการวางแผนการพัฒนาสำหรับ Mobile native app ในลำดับถัดไป

- OTA integration: ไม่ทำ เนื่องจากมีความซับซ้อนมากเกินความจำเป็นสำหรับ Scope ของโปรเจค ณ ตอนนี้

- Real payment: ยังไม่ทำ เพราะด้วยระยะเวลาในการทำโปรเจคที่มีจำกัด จะยังไม่มีการทำขั้นตอนในการชำระเงินจริงๆ แต่จะใช้แบบ Test mode แทน ซึ่งก็จะมีเป้าหมายเดียวกันคือ เป้นแนวทางแบบ Payment process จริงๆ แต่ไม่มีการเรียกชำระเงินจริง (เป็นแบบ Test payment) แต่ในอนาคตจะมีการพัฒนาให้เชื่อมกับ API ของจริง

- Dynamic pricing - ML - based: ยังไม่ทำในตอนนี้ เพราะมีการตัดสินใจที่เกี่ยวข้องในการคำนวณราคาของห้องพักอยู่แล้วใน Feature หลักผ่านการทำงานของ Staff ในตำแหน่ง Manager และ ML - based เป็น Feature รองและเนื่องจากที่จะต้องทำ Integration LLM ด้วยแต่โปรเจคนี้มีระยะเวลาที่จำกัด ทำให้ไม่สามารถทำ Feature นี้ในตอนนี้ได้ แต่จะพิจารณาให้มีการพัฒนาในอนาคตแน่นอนหากมีโอกาส

- Internationalization (i18n): จะยังไม่ทำภาษาอื่นนอกจากภาษาไทยในตอนนี้ เนื่องจากกลุ่มเป้าหมายของลูกค้าโปรเจคเรา (แม้จะทำเพื่อการศึกษา) ณ ตอนนี้คือโรงแรมขนาดเล็กถึงขนาดกลางที่อยู่ในประเทศไทย จึงจะมีการพัฒนาเป็นภาษาไทยไปก่อนในตอนนี้และจะมีการวางแผนในการพัฒนาเพิ่มภาษาอื่นๆ ในอนาคตอันใกล้ด้วย และการทำ i18n เองก็จะเป็นการเพิ่มความซับซ้อนของการทำงาน เพราะจะต้องมีการแปลภาษาให้กับเนื้อหาในทุกๆ หน้าผ่านการทำ Translation function

- Multi - currency: ยังไม่ทำ เพราะเป้าหมายที่เราโฟกัสในตอนนี้คือโรงแรมที่อยู่ภายในประเทศไทย การพัฒนาให้เปิดรับเงินตราจากสกุลเงินอื่นในตอนนี้จะนำมาซึ่งความซับซ้อนมากเกิดความจำเป็น แต่จะมีการวางแผนดำเนินการใน Version ถัดๆ ไป

- Channel manager: จะยังไม่มีการทำในตอนนี้ เนื่องด้วยข้อจำกัดของระยะเวลาในการดำเนินงาน การที่จะต้องกระจายห้องพักไปให้ลูกค้าจากที่อื่นเห็น ในตอนนี้จะทำเป็นแบบกึ่ง Marketing ไปก่อน แต่จะมีการวางแผนสำหรับการพัฒนา Feature นี้ในอนาคตด้วยเช่นเดียวกันหากมีโอกาส

## Section 8: Success Criteria

- Technical:
    - Test coverage >= 60% (Critical paths 100%)
    - Lighthouse score >= 85 ในทุกหน้าหลัก
    - CI/CD pipeline ทำงานได้อย่างครบถ้วน (ทั้ง Lint, Test, Build และ Deploy)
    - ไม่เกิด Over booking ใน Concurrent booking test

- Functional:
    - ผู้ทดสอบ 3 - 5 คน สามารถทำ end - to - end booking flow ได้โดยไม่ต้องสอนการใช้งาน
    - ทุก User role ใช้ Feature ของตัวเองได้อย่างครบถ้วนและไม่มี User Role ใดเห็นหรือใช้งาน Feature ที่ไม่ใช่ของ Role ตัวเองได้

- Portfolio:
    - ไฟล์ README.md สมบูรณ์ มี Live demo และ Demo accounts ในทุก Role
    - สามารถทำความเข้าใจและเล่าสิ่งที่ทำต่างๆ ใน Project ได้ตั้งแต่เริ่มต้นทำงาน (ตั้งแต่ขั้นตอนการวางแผน) ภายในระยะเวลาที่เหมาะสม (ประมาณ 25 - 30 นาที)
